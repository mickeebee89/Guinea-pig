### 🟢 P7 — DOUBLE-BOOKING RACE (new issue found 14 Jul) — DONE + verified (DB guard live + 23505 handler reviewed)
> **Numbering note:** this was a NEW issue that surfaced during testing on 14 Jul, numbered **P7** so it does NOT collide with the still-open **P5 (notification-type audit + remove the non-functional notification toggles)** and **P6 (email / forgot-password UX)** — both of those remain **OPEN / not started**.

Slot-collision prevention was **display-time only**: the model booking wizard greys out slots already held by pending/accepted sessions (server RPC `taken_slots`), then inserts a `sessions` row with **no pre-insert re-check, no transaction, and no DB uniqueness** (`availability_id` is a non-unique FK; no unique constraint on `sessions` anywhere). Two models racing for the same free slot could **both** insert active bookings — a time-of-check/time-of-use race. Sequential booking was always safe; completing/declining/cancelling correctly frees a slot (unchanged, by design).
- **Fix — DB atomic guard (LIVE + verified):** partial unique index `sessions_active_slot_uniq` on `(provider_id, date, start_time)` `where status in ('pending','accepted')` — the second concurrent insert now fails atomically. Active-only, so completed/declined/cancelled still re-open the slot (matches `taken_slots`). SQL saved to `supabase/booking-guard.sql` (with a pre-check for existing dupes — returned clean). Index confirmed present in `pg_indexes`.
- **Fix — friendly client handling (built, typechecks clean):** the losing insert (Postgres **`23505`**) now shows *"That time was just booked — please choose another time,"* refreshes `taken_slots` so the slot flips to "Booked" (new `takenNonce` bump), and returns the wizard to the time step. Any other error keeps the generic path. `apply-session.tsx`.
- **Display-time `taken_slots` filtering kept as the friendly first line of defence.** No change to availability, `has_open_availability`, or completion/lifecycle semantics.
- **Verified:** SQL test — a duplicate active insert is rejected with **23505**; and the `apply-session.tsx` handler reviewed — targeted `23505` catch, friendly alert, slot flips to "Booked", wizard returns to slot picker. ⚠️ Live-DB change (index also listed in notes "Live DB changes").

### 🟢 P4 — COMPLETED-CHAT VISIBILITY + REALTIME UNREAD BADGE DONE + verified on two phones
A four-symptom bug cluster around completed chats + the unread badge that collapsed to **two root causes**. **Client-side JS only** — no SQL, no edge deploy, no native rebuild (`messages` is already in the realtime publication; RLS on `messages` is participant-scoped, not status-scoped, so completed chats were always readable at the DB level; admin moderation read-access and report-from-chat were unaffected).
- **Root cause A — "completed = invisible & unreachable."** The inbox query (`messages.tsx`) bucketed `completed` with `cancelled`/`declined` and filtered it out — yet a completed chat is still readable (chat screen loads `accepted||completed`, renders read-only) and reachable via the `session_accepted`/`new_message` notification deep-link. This one filter caused **Bug 1** (chat vanishes), **Bug 3** (stuck dot: HeaderIcons counted unread in `accepted`+`completed` but the list hid completed and its badge counted `accepted`-only, so the chat was unreachable to run mark-as-read → dot stuck; only cleared when the other user was deleted), and **Bug 4**'s "vanish" perception.
- **Root cause B — "badge focus-polled, not realtime."** `HeaderIcons`/`messages.tsx` recalculated only via `useFocusEffect`; the app's only realtime subscription lived in the chat screen. → **Bug 2**.
- **Fixes (`mobile/src/app/(app)/messages.tsx` + `mobile/src/components/HeaderIcons.tsx`):** (1) inbox filter → excludes only `(cancelled,declined)` so completed returns; (2) unread gate counts `accepted`+`completed` (matches HeaderIcons) — opening the now-reachable completed chat runs the existing mark-as-read, which is how the dot clears; (3) completed chats grouped into a collapsible **"Past chats"** section (`FlatList`→`SectionList`), rendered read-only with a check badge + "Completed" tag instead of the 🔒 lock; (4) both screens subscribe to `messages` postgres_changes (unique channel per mount, 300 ms debounce) → live badge, not just on focus.
- **Bug 4 = saved-but-hidden, not dropped.** The message insert has no status guard and RLS isn't status-scoped, so an at-completion send saves fine; surfacing completed chats reveals it — no code change. Deliberately **not** force-marking-read on completion (would falsely clear the other party's genuine unreads).
- **Verified on two phones:** completed chat shows in "Past chats" read-only ✅; stuck dot clears on open + stays clear on focus ✅; realtime badge updates live on both model home + provider dashboard ✅; at-completion message present in Past chats ✅.
